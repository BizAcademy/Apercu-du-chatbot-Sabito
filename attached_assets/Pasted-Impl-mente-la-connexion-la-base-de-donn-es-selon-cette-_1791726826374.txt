Implémente la connexion à la base de données selon cette architecture MySQL/MariaDB :

- Le backend Node.js/TypeScript est le seul à se connecter directement à la base.
- Utilise le package mysql2/promise et une connexion par pool.
- Ne connecte jamais le navigateur directement à MySQL.
- Ne remplace pas MySQL/MariaDB par PostgreSQL, Supabase ou DATABASE_URL.
- Avant de modifier le projet, inspecte son architecture et adapte cette solution sans remplacer les bibliothèques non liées.

Configuration par variables d’environnement ou Secrets, sans inscrire ni afficher les valeurs dans le code, le frontend, les journaux ou la conversation :
- MYSQL_HOST : obligatoire
- MYSQL_DATABASE : obligatoire
- MYSQL_USER : obligatoire
- MYSQL_PASSWORD : obligatoire
- MYSQL_PORT : facultatif, valeur par défaut 3306

Valide la présence des quatre variables obligatoires et vérifie que le port est un entier entre 1 et 65535. Nettoie les espaces autour de MYSQL_HOST, MYSQL_DATABASE, MYSQL_USER et MYSQL_PORT, mais ne modifie pas MYSQL_PASSWORD.

Crée un module de connexion qui expose :
- getMysqlPool() : retourne un pool singleton créé à la première utilisation ;
- checkMysqlConnection() : vérifie la connexion par SELECT 1 ;
- closeMysqlPool() : ferme le pool proprement à l’arrêt.

Paramètres exacts du pool :
{
  host,
  port,
  database,
  user,
  password,
  waitForConnections: true,
  connectionLimit: 10,
  multipleStatements: true
}

Utilise les paramètres SQL `?` pour toutes les valeurs reçues à l’exécution ; ne construis pas des requêtes par concaténation de valeurs. Pour une transaction, récupère une connexion du pool, appelle beginTransaction(), puis commit() en cas de succès ou rollback() en cas d’erreur, et release() dans un bloc finally.

Environnements :
- En production Plesk, configure MYSQL_HOST=localhost et MYSQL_PORT=3306 uniquement si l’API et MariaDB/MySQL sont sur le même serveur Plesk.
- En développement ou dans un aperçu Replit, utilise une base de test isolée. Ne pointe pas localhost vers la production et ne réutilise jamais les identifiants de production pour les tests.
- Configure les valeurs sensibles dans le gestionnaire de Secrets ou l’environnement du serveur. Ne crée pas de variables frontend `VITE_*` pour les identifiants MySQL.

Migrations :
- Place les migrations MySQL dans migrations/mysql/ et trie-les par numéro de fichier.
- Garde une table de suivi avec cette structure :
  CREATE TABLE IF NOT EXISTS schema_migrations (
    name VARCHAR(255) NOT NULL PRIMARY KEY,
    applied_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
  ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
- Applique seulement les migrations qui ne figurent pas déjà dans schema_migrations, puis inscris leur nom après application.
- En production, vérifie l’historique et l’impact avant toute migration ; ne rejoue pas aveuglément les anciennes migrations et ne fais aucune migration destructive sans validation.

Garde toute intégration Supabase éventuellement nécessaire séparée de cette connexion MySQL : les variables VITE_SUPABASE_URL et VITE_SUPABASE_ANON_KEY ne sont pas des paramètres MySQL, et un secret de service ne doit jamais être exposé au navigateur.

Ajoute ou adapte les tests pour vérifier la validation de configuration, le port invalide, SELECT 1, la fermeture du pool et le nettoyage des transactions. Ne révèle aucun secret dans les tests ou leurs sorties.
